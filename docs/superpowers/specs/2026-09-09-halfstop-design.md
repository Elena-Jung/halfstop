# halfstop 설계

- 작성일: 2026-09-09
- 상태: 승인됨
- 다음 단계: 구현 계획 작성

## 배경

사진에 촬영 정보 프레임을 붙여 다시 내려받는 웹앱을 새로 만듭니다. Node 22와 npm 10
환경이고 디렉터리는 비어 있습니다.

만드는 사람이 곧 사용자입니다. 직접 찍은 사진을 정리할 때 쓰려고 만드는 도구이므로, 기능은
실제로 아쉬웠을 때 늘립니다. 선행 사례에 있다는 이유만으로 따라 넣지 않습니다. 출력 비율
강제처럼 처음에 검토했다가 뺀 기능이 여기에 해당합니다.

이름은 `halfstop`입니다. 노출을 반 스톱 올린다는 사진 용어에서 가져왔습니다. 같은 문제를 푸는
선행 프로젝트가 `exif-frame`이라는 이름으로 이미 앱스토어와 플레이스토어까지 나가 있어,
검색에서 섞이지 않도록 다르게 잡았습니다. 작업 디렉터리 이름은 `exifframe`으로 남아 있지만
저장소와 패키지 이름은 `halfstop`을 씁니다.

핵심 제약은 이미지를 서버에 보내지 않는 것입니다. 업로드 자체가 없으므로 정적 빌드만 배포하면
"서버에 저장하지 않는다"가 약속이 아니라 구조로 보장됩니다. 모든 디코딩, 합성, 인코딩은
브라우저 안에서 끝납니다.

## 선행 사례: exif-frame

같은 문제를 푸는 오픈소스 프로젝트가 이미 있습니다.
[jeonghyeon-net/exif-frame](https://github.com/yurucam/exif-frame)이고 스타 119개,
TypeScript, GPL-3.0이며 2026년 5월까지 갱신되고 있습니다. Capacitor로 iOS와 Android 앱도
배포합니다. 테마가 16종입니다.

**GPL-3.0이므로 코드와 로고 이미지를 가져다 쓸 수 없습니다.** 같은 라이선스로 공개할 것이
아니라면 설계 아이디어만 참고합니다.

### 받아들이는 것

- **선언적 옵션 스키마.** 각 테마가 `{ id, type, default, min, max, options, description }`
  형태로 옵션을 데이터로 선언하고, 설정 UI를 그 선언에서 자동으로 만듭니다. 프리셋마다 설정
  패널을 따로 만들 필요가 없어집니다.
- **템플릿 토큰.** 표시 항목을 체크박스로 켜고 끄는 대신
  `{MAKER}{BODY}{LENS}{ISO}{MM}{F}{SEC}{TAKEN_AT}` 토큰이 담긴 문자열 한 줄과 구분자
  설정으로 다룹니다. 항목뿐 아니라 순서까지 사용자가 정할 수 있고 UI는 입력란 하나로 끝납니다.
- **필름과 중형 브랜드.** 로고 목록에 Contax, Mamiya, Phase One, Epson, Ricoh를 넣습니다.
  필름 스캔 사용자에게는 현행 디지털 브랜드보다 이쪽이 중요합니다.

### 다르게 가는 것

- 이 프로젝트의 테마 시그니처는 `(photo, input, store) => HTMLCanvasElement`입니다. 테마가
  캔버스를 직접 만들고 컨텍스트를 직접 호출합니다. 그 결과 `render.ts`가 전체 해상도로 그린
  캔버스를 나중에 축소하므로 텍스트가 큰 크기로 래스터화된 뒤 리샘플링됩니다. 워커로 옮길 수
  없고 DOM 없이 테스트할 수도 없습니다. 레이아웃과 페인팅을 분리하는 우리 설계가 이 세 가지를
  모두 피합니다.
- 옵션값이 절대 픽셀입니다. 같은 설정이 1200만 화소 사진과 4500만 화소 사진에서 전혀 다르게
  보입니다. 우리는 디자인 단위를 써서 사진 크기와 무관하게 같은 결과를 냅니다.
- 웹에서 HEIC와 RAW를 지원하지 않습니다. 의존성에 디코더가 없고, 모바일 앱은 네이티브 피커가
  JPEG를 넘겨주는 방식으로 우회합니다. 우리는 브라우저에서 직접 처리합니다.
- 출력 이미지에 `exif-restorer`로 원본 EXIF를 다시 넣습니다. 우리는 제거합니다.

## 확정된 요구사항

브레인스토밍에서 사용자가 직접 정한 내용입니다.

- 프레임 프리셋 3종을 모두 지원하고 사용자가 고릅니다. 하단 정보 바, 4면 여백 액자, 사진 위
  반투명 오버레이.
- 바디와 렌즈 브랜드 SVG 로고를 저장소에 번들하고, 매칭에 실패하면 브랜드명을 텍스트
  워드마크로 렌더링합니다.
- 여러 장을 한 번에 처리하고 ZIP으로 내려받습니다.
- HEIC와 HEIF 입력을 지원합니다.
- RAW는 내장 JPEG 프리뷰를 추출하는 방식으로 지원합니다.
- EXIF 값을 사용자가 직접 고칠 수 있습니다.
- 출력 포맷에 WebP를 포함합니다. JPEG와 PNG도 함께 제공합니다.
- 촬영일시를 프레임에 표시합니다. 표기 형식을 고를 수 있습니다.
- 출력 해상도는 내보낼 때마다 사용자가 고릅니다. 원본, 4K(긴 변 3840px),
  2K(긴 변 1920px), SNS(긴 변 1080px).
- 출력 이미지에는 원본 EXIF를 다시 넣지 않습니다.
- 정적 호스팅에 공개 배포합니다.
- UI는 한국어와 영어를 함께 제공합니다.
- 한국어 문구는 화면에 보이는 것까지 모두 습니다체로 씁니다. 해요체를 쓰지 않습니다.
- 옵션을 바꿀 때 미리보기가 곧바로 반응합니다. 전체 해상도 작업은 내보낼 때만 합니다.

## 프레임에 표시하는 항목

프리셋 세 개가 공통으로 다루는 정보입니다. 표시 여부와 순서는 체크박스가 아니라 템플릿
문자열로 정합니다. 예를 들어 `{MAKER} {BODY} | {LENS}` 처럼 쓰면 그대로 그려집니다. 설정은
브라우저에 저장해 다음 방문에도 유지합니다.

| 항목 | 출처 | 비고 |
|---|---|---|
| 바디 브랜드 로고 | `Make` | 매칭 실패 시 텍스트 워드마크 |
| 바디 모델명 | `Model` | Make 접두사 제거 후 표기 정리 |
| 렌즈 브랜드 로고 | `LensMake`, `LensModel` | 서드파티 렌즈 판별을 바디 브랜드 상속보다 먼저 수행 |
| 렌즈 모델명 | `LensModel` | 없으면 `LensSpecification`으로 대체 |
| 초점거리 | `FocalLength`, `FocalLengthIn35mmFilm` | 환산값 병기 여부를 선택 |
| 조리개 | `FNumber` | `f/1.8` 형식 |
| 셔터 속도 | `ExposureTime` | 1초 미만은 분수, 이상은 초 |
| ISO | `ISOSpeedRatings` | |
| 촬영일시 | `DateTimeOriginal` | `{TAKEN_AT}`, 표기 형식 선택 |

각 항목에는 템플릿 토큰이 붙습니다. `{MAKER}`, `{BODY}`, `{LENS}`, `{MM}`, `{F}`, `{SEC}`,
`{ISO}`, `{TAKEN_AT}`입니다. 값이 없는 토큰은 구분자와 함께 통째로 사라집니다.

프리셋 옵션은 코드가 아니라 선언으로 둡니다.

```ts
type PresetOption =
  | { id: string; type: 'color';   default: string }
  | { id: string; type: 'number';  default: number; unit: 'u' }
  | { id: string; type: 'boolean'; default: boolean }
  | { id: string; type: 'select';  options: string[]; default: string }
  | { id: string; type: 'range';   min: number; max: number; step: number; default: number }
  | { id: string; type: 'text';    default: string };
```

설정 패널은 이 선언에서 자동으로 만듭니다. 프리셋을 추가할 때 UI 코드를 새로 쓰지 않습니다.
크기를 뜻하는 옵션의 단위는 픽셀이 아니라 디자인 단위입니다. 사진 화소수가 달라져도 같은
설정이 같은 결과를 냅니다.

## 기술 스택

Vite와 React 19, TypeScript로 만든 단일 정적 SPA입니다. 서버 코드가 없으므로 프레임워크는
번들러 역할만 합니다.

라이브러리는 npm 레지스트리에서 실제로 확인한 최신 버전입니다.

| 용도 | 선택 | 근거 |
|---|---|---|
| EXIF 파싱 | `exifreader` 4.44.1 | 2026년 9월까지 갱신 중이며 JPEG, TIFF 계열 RAW, HEIC, PNG, WebP를 모두 다룹니다. 후보였던 `exifr`은 2022년 이후 갱신이 없습니다. |
| HEIC 디코딩 | `heic-to` 1.5.2 | libheif WASM 래퍼입니다. npm 패키지 전체는 23MB지만 여러 빌드 변형을 포함한 크기이고, 실제로는 단일 스레드 빌드 하나만 지연 로드합니다. |
| RAW 프리뷰 | 자체 TIFF IFD 파싱 우선, 실패 시 `libraw-wasm` 1.6.0 (1.98MB) | 대부분의 RAW는 IFD를 직접 훑어 가장 큰 내장 JPEG을 꺼낼 수 있습니다. WASM은 그 경로가 실패했을 때만 불러옵니다. |
| ZIP 생성 | `client-zip` 2.5.0 (40KB) | 스트리밍 방식이라 배치 결과를 메모리에 한꺼번에 쌓지 않습니다. |

i18n은 라이브러리 없이 타입이 붙은 사전 모듈로 처리합니다. 문자열이 수십 개 수준이라
`react-i18next`를 넣을 이유가 없습니다.

## 배포

Cloudflare Pages에 올리고 GitHub Actions로 자동 배포합니다. `SharedArrayBuffer`를 쓰지 않는
설계라 COOP와 COEP 헤더가 필요 없습니다.

배포 전에 컨테이너로 프로덕션 빌드를 확인합니다. 개발 서버에서는 드러나지 않는 실패가 셋
있기 때문입니다.

- 워커는 프로덕션 빌드에서 별도 청크로 떨어지고 URL이 재작성됩니다. 정적 서버가 그 청크를
  `text/plain`으로 내보내면 모듈 워커가 로드를 거부하고 내보내기만 조용히 실패합니다.
  미리보기는 멀쩡해서 알아채기 어렵습니다.
- `?url`로 가져온 폰트는 해시가 붙은 자산 경로가 됩니다. 서버가 `font/woff2`를 모르면
  `FontFace` 등록이 실패하고 내보낸 파일만 대체 서체로 나옵니다.
- 하위 경로에서 서비스하면 `import.meta.url` 기반 워커 해석과 자산 URL이 깨집니다.

컨테이너는 2단계로 만듭니다. `node:22-alpine`에서 `npm ci`와 빌드를 하고, `nginx:alpine`에
`dist/`만 복사합니다. 여기 쓰는 `nginx.conf`가 실제 호스트가 갖춰야 할 조건의 명세 역할을
하며, Cloudflare Pages에서는 같은 내용을 `_headers` 파일로 옮깁니다.

| 헤더 | 값 | 이유 |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | 워커 청크의 MIME이 틀렸을 때 조용히 넘어가지 않고 실패하게 합니다 |
| `Content-Security-Policy` | `default-src 'self'; img-src 'self' blob: data:; worker-src 'self' blob:; connect-src 'self'; object-src 'none'; base-uri 'none'` | 이미지가 브라우저 밖으로 나가지 않는다는 약속을 구조로 강제합니다 |
| `Cache-Control` (해시 자산) | `public, max-age=31536000, immutable` | 파일명에 해시가 붙어 있어 안전합니다 |
| `Cache-Control` (`index.html`) | `no-cache` | 새 배포가 즉시 반영되어야 합니다 |

CSP의 `connect-src 'self'`가 특히 중요합니다. 나중에 누가 실수로 업로드 코드를 넣어도
브라우저가 막습니다. 사생활 보호가 문서상의 약속이 아니라 실행 환경의 제약이 됩니다.

GitHub Actions는 push마다 타입 검사와 테스트를 돌리고 통과하면 배포합니다. 테스트가 매번
도는 것이 자동화의 실질적인 이득이고 배포는 덤입니다.

### 사용 통계

Cloudflare Web Analytics를 씁니다. 호스팅과 같은 곳이라 설정이 한 번이고, 쿠키를 쓰지 않으며
개인을 식별하지 않습니다. 그래서 위 CSP를 거의 그대로 유지할 수 있고 동의 배너도 필요하지
않습니다.

구글 애널리틱스를 검토했다가 뺐습니다. GA4를 넣으려면 `script-src`에 태그 관리자를,
`connect-src`에 애널리틱스 도메인을 열어야 합니다. 사진 자체는 여전히 나가지 않지만, 그
사실을 CSP가 더는 강제하지 못하고 코드 리뷰로 지키는 약속으로 내려앉습니다. 쿠키 동의 문제도
따라옵니다. 프리셋별 사용률 같은 상세 이벤트가 실제로 아쉬워지면 그때 다시 봅니다.

### 검색 노출

`index.html`에 소개 내용을 직접 넣고 React는 그 아래에 마운트합니다. 지금 구조로는 색인될
텍스트가 없기 때문입니다. 본문이 자바스크립트로만 그려지면 크롤러가 제대로 읽지 못하고,
게다가 이 도구의 실제 결과물은 사용자가 파일을 넣어야 나오므로 애초에 색인 대상이 아닙니다.
메타 태그만 붙이는 것으로는 해결되지 않습니다.

넣을 것은 다음과 같습니다.

- 페이지 내용을 정확히 설명하는 `<title>`과 `<meta name="description">`
- 실제 `<h1>`과 도구가 무엇을 하는지 설명하는 문단
- 결과물 스크린샷과 그 `alt` 텍스트
- Open Graph 태그. 링크를 공유했을 때 미리보기가 나오게 합니다
- `robots.txt`, `sitemap.xml`, canonical URL

받아들이는 제약이 하나 있습니다. i18n이 클라이언트 토글이라 색인은 한 언어로만 됩니다.
두 언어를 모두 노출하려면 `/ko`와 `/en`처럼 URL을 갈라 `hreflang`을 붙여야 하는데, 지금은
그만큼의 값어치가 없다고 봅니다. 필요해지면 그때 나눕니다.

구글 문서가 하지 말라고 명시한 것들은 하지 않습니다. `meta keywords`는 검색에 쓰이지 않고,
콘텐츠 길이는 순위와 무관하며, 도메인 이름에 키워드를 넣는 것도 거의 영향이 없습니다.

## 렌더링 구조

이 앱에서 가장 틀리기 쉬운 지점은 미리보기와 실제 내보내기가 어긋나는 것입니다. 레이아웃을
두 번 작성하면 반드시 어긋납니다. 세 가지 방식을 놓고 비교했습니다.

- **DOM을 그린 뒤 래스터화:** 내부적으로 SVG `foreignObject`를 쓰므로 폰트를 base64로
  인라인해야 하고, 한글 폰트에서는 감당하기 어렵습니다. 워커에서도 못 돕니다. 제외합니다.
- **SVG를 만든 뒤 래스터화:** 같은 폰트 인라인 문제가 있고 Safari에서 크기 처리가 불안정합니다.
  SVG는 로고 원본 형식으로만 남깁니다.
- **Canvas2D에 배율을 곱해 직접 그리기:** 채택합니다. 워커에서 안전하게 돌고, 결정적이며,
  `convertToBlob`으로 WebP와 JPEG, PNG를 바로 뽑습니다.

여기에 한 겹을 더 둡니다. 프리셋이 캔버스 컨텍스트를 직접 받으면 무엇이든 할 수 있게 되어
추상화가 새고, 테스트도 워커 이전도 어려워집니다. 그래서 레이아웃과 페인팅을 분리합니다.

```
layout(input: LayoutInput, services: LayoutServices) -> Scene   // 순수 함수, 캔버스 없음
paint(scene: Scene, ctx: Ctx2D, pxPerUnit: number)              // 프리셋 공용 구현 하나
```

- `Scene`은 `image`, `text`, `path`, `rect`, `group` 원시 노드로 이루어진 불변 트리입니다.
  좌표 단위는 픽셀이 아니라 디자인 단위이고, `1u = 사진 짧은 변 / 1000`으로 둡니다. 해상도
  독립성이 규칙이 아니라 자료 구조로 보장됩니다.
- 레이아웃이 순수하지 않게 되는 유일한 지점 두 가지는 서비스로 주입합니다.
  `measureText(text, style)`과 `getLogo(brandId)`입니다.
- 미리보기와 내보내기는 `pxPerUnit`만 다른 같은 `paint` 호출입니다. 미리보기가 축소된
  비트맵을 쓴다는 차이는 `image` 노드 안에 있을 뿐 레이아웃에는 없습니다. 자세한 내용은
  아래 반응 속도 절에 있습니다.

`core/` 아래 코드는 React를 import 하지 않고 `document`를 만지지 않습니다. 이 규칙을 처음부터
지켜야 나중에 워커로 옮길 수 있습니다.

### 워커에서 그리기 위해 미리 정해둘 것

- **로고는 빌드 시점에 SVG에서 `Path2D` 경로 데이터로 변환합니다.** 워커 캔버스에는
  `HTMLImageElement`가 없어 SVG를 그릴 수 없습니다. 경로로 바꾸면 배율과 무관하게 선명하고,
  색도 프리셋에 맞춰 바꿀 수 있습니다.
- **폰트는 워커 안에서 `FontFace`를 ArrayBuffer로 만들어 `self.fonts.add()` 한 뒤 준비가
  끝날 때까지 기다립니다.** 이런 종류의 앱에서 가장 흔한 버그가 폰트 로드 전에 내보내기가
  실행되어 결과물만 대체 서체로 나오는 것입니다.
- 폰트는 자체 호스팅합니다. EXIF 텍스트는 사실상 ASCII이므로 캔버스용 라틴 서브셋을 기본으로
  싣고, 한글 자소가 필요한 경우는 사용자가 직접 입력한 문자열뿐이므로 그때 한글 서브셋을
  추가로 불러옵니다.

## 촬영 정보가 없는 사진

EXIF 가 없는 사진을 넣으면 프레임의 정보 바가 빈 채로 나옵니다. 사용자는 왜 비었는지 알 수
없고, 도구가 고장 났다고 여기기 쉽습니다. 그래서 넣기 전에 확인을 받습니다.

**판정 기준은 EXIF 블록의 유무가 아니라 프레임에 그릴 값이 하나라도 있는지입니다.** 방향
정보만 있고 카메라 정보가 없는 파일은 EXIF 가 있어도 바가 빕니다. 사용자가 걱정하는 것은
그쪽입니다. `toFields` 의 결과가 비어 있으면 촬영 정보가 없는 것으로 봅니다.

### 묻는 방식

여러 장을 넣을 때 **파일마다 묻지 않습니다.** 스무 장을 떨어뜨리고 확인을 열두 번 누르게 하면
쓸 수 없습니다. 한 번만 묻고 개수를 알립니다.

전부 촬영 정보가 있으면 묻지 않고 그대로 넣습니다. 일부라도 없으면 이렇게 묻습니다.

> 3장에 촬영 정보가 없습니다. 그래도 넣겠습니까?
>
> `모두 넣기` `EXIF 있는 이미지만 넣기` `검토하기`

앞의 둘은 그 자리에서 끝납니다. **`검토하기` 는 목록 화면을 엽니다.** 어떤 파일에 정보가
없는지 보고 한 장씩 고르고 싶을 때를 위한 것입니다. 스무 장 중 세 장이 빠졌을 때, 그 세 장이
무엇인지 모르고 결정하라는 것은 무리입니다.

### 검토 화면

- 넣으려는 파일을 전부 목록으로 보여줍니다. 파일 이름, 작은 미리보기, 읽어낸 촬영 정보를
  한 줄에 담습니다.
- 촬영 정보가 없는 줄은 눈에 띄게 표시하되 **색만으로 구분하지 않습니다.** 글자나 아이콘을
  함께 씁니다.
- 줄마다 체크 상자를 두어 넣을 것을 고릅니다. 처음에는 정보가 있는 것만 켜 둡니다.
- 전체 선택과 전체 해제를 둡니다.
- 확정하면 켜진 것만 넣습니다.

체크 상자마다 어느 파일인지 알 수 있는 이름이 있어야 합니다. 이름이 `체크박스` 로만 읽히면
목록의 뜻이 사라집니다.

### 파일이 한 장일 때

`검토하기` 는 고를 것이 없으므로 두지 않습니다. `넣기` 와 `취소` 만 둡니다.

### 확인 창의 접근성

브라우저의 `confirm()` 을 쓰지 않습니다. 꾸밀 수 없고 화면 전체를 멈추며 어두운 테마와도
어긋납니다. 직접 만들되 다음을 지킵니다.

- `role="dialog"` 와 `aria-modal="true"`, 그리고 제목과 이어지는 `aria-labelledby`
- 열릴 때 포커스가 창 안으로 들어가고 창 밖으로 나가지 않습니다
- Escape 로 닫히며, 닫으면 포커스가 열기 전 자리로 돌아갑니다
- 어느 버튼이 기본 동작인지 시각과 포커스 순서 양쪽에서 분명해야 합니다

### 구현 메모

판정하려면 넣기 전에 파일마다 EXIF 를 읽어야 합니다. 스무 장이면 스무 번입니다. 파일 전체를
`ArrayBuffer` 로 읽지 말고 앞부분만 잘라 읽습니다. EXIF 는 파일 머리에 있습니다.

## 화면 구조

라이트룸 모바일의 편집 화면을 기준으로 삼습니다.

- **오른쪽 끝에 세로 아이콘 레일.** 도구 묶음마다 아이콘 하나입니다. 지금 열려 있는
  묶음은 둥근 사각 배경으로 표시합니다.
- **레일 왼쪽에 패널이 열립니다.** 접히는 절로 나뉘고 절마다 제목이 붙습니다.
- **슬라이더는 레이블이 왼쪽, 현재 값이 오른쪽,** 그 아래 트랙과 둥근 핸들입니다. 값이
  양수와 음수로 갈리는 항목은 트랙 가운데를 기준으로 채웁니다.
- **어두운 테마가 기본입니다.** 편집 화면이 밝으면 주변 밝기가 사진 판단을 흐립니다.
  사진 도구가 대체로 어두운 이유입니다.

참고한 화면 위쪽에 `ISO 100 39mm f/5.6 1/500초` 띠가 있는데, 이것이 우리가 프레임에 그리는
바로 그 값입니다. 편집 대상이 아니라 확인 대상이므로 패널이 아니라 사진 가까이 둡니다.

### 설계에 미치는 영향

- 아이콘 레일과 패널의 짝은 탭 구조입니다. WAI-ARIA 의 `tablist`, `tab`, `tabpanel` 역할을
  그대로 씁니다. 아이콘만 있는 버튼이므로 각각에 접근 가능한 이름이 필요합니다.
- 옵션을 묶음으로 나눠야 하므로 `PresetOption` 에 소속 묶음을 나타내는 자리가 필요합니다.
  레이블과 마찬가지로 번역 키를 담습니다.
- 아이콘 세트를 하나 정해야 합니다.
- 어두운 테마가 기본이므로 명암 대비 검사는 어두운 배경에서 먼저 합니다.

## 접근성

[W3C WAI 표준](https://www.w3.org/WAI/standards-guidelines/ko) 가운데 이 프로젝트에 해당하는 것은
둘입니다. 콘텐츠 기준인 **WCAG 2**와, 동적 UI의 역할과 상태를 표현하는 **WAI-ARIA**입니다.
나머지 ATAG는 저작 도구, UAAG는 브라우저 개발자를 위한 것이라 해당하지 않습니다.

**목표 수준은 WCAG 2.2 AA입니다.** AAA는 이 도구의 성격상 맞지 않는 항목이 섞여 있어 잡지
않습니다.

이 앱에서 특히 중요한 지점이 있습니다. **결과물이 캔버스 픽셀입니다.** 화면에 그려진 프레임과
촬영 정보는 스크린 리더에게 아무것도 아닙니다. 그림 안의 글자는 읽히지 않습니다. 그래서 캔버스
바깥에 같은 정보를 텍스트로 내놓아야 합니다.

### 지킬 것

### 설계에 미치는 영향

옵션 선언에 사람이 읽는 레이블 자리가 필요합니다. `PresetOption` 에 `label` 을 넣되, 번역된
문자열이 아니라 **키**를 담습니다. `core` 는 번역하지 않는다는 원칙을 지키기 위해서입니다. UI 가
그 키를 로케일에 맞춰 번역합니다. 옵션마다 짧은 설명이 필요한 경우도 있으므로 `description`
키도 함께 둡니다.

캔버스의 `aria-label` 은 `Scene` 이 아니라 이미 계산해 둔 표시 문자열에서 만듭니다. 프레임에
그린 것과 읽어주는 것이 어긋나지 않게 하려면 같은 출처를 써야 합니다.

### 1단계 뼈대에서 확인된 위반

다음 계획에서 UI 를 제대로 만들 때 해소합니다.

- `<canvas>` 에 접근 가능한 이름이 없습니다. 결과물 자체가 스크린 리더에 전달되지 않습니다.
- 상태 문구가 바뀌어도 알리지 않습니다. `aria-live` 영역이 없습니다.
- 옵션 레이블이 `BACKGROUND`, `BAR_HEIGHT` 같은 내부 식별자 그대로입니다.
- 배경색과 글자색을 지정하지 않아 어두운 테마에서 대비가 부족합니다.
- 드롭 영역이 `div` 라 시맨틱이 없습니다. 파일 선택 입력이 있어 키보드로 막히지는 않지만,
  영역의 용도가 보조 기술에 전달되지 않습니다.

## 반응 속도

프레임 설정은 눈으로 보면서 맞추는 작업입니다. 옵션을 하나 건드릴 때마다 몇 초씩 기다리면
도구로 쓸 수 없습니다. 미리보기와 내보내기의 비용을 처음부터 갈라 둡니다.

- 파일을 받으면 EXIF를 먼저 읽고, `createImageBitmap`의 `resizeWidth` 또는 `resizeHeight`로
  긴 변 1600px짜리 비트맵만 디코딩합니다. 4500만 화소 원본을 통째로 디코딩하지 않으므로 첫
  결과가 빨리 뜨고 메모리도 훨씬 적게 씁니다. 어느 축을 줄일지는 EXIF에 적힌 원본 크기로
  정하고, 그 값이 없으면 가로를 기준으로 잡습니다.
- 옵션이 바뀌면 디코딩을 다시 하지 않습니다. `layout()`을 다시 돌리고 1600px 캔버스에
  `paint()`만 다시 합니다. 이 경로에는 인코딩도 objectURL 발급도 없습니다. 화면에 보이는
  캔버스에 직접 그립니다.
- 전체 해상도 디코딩과 인코딩은 내보내기를 누른 순간에만 합니다. 끝나면 비트맵과 캔버스를
  즉시 해제합니다. 평소에는 큰 비트맵을 아예 들고 있지 않습니다.

미리보기와 내보내기가 같은 `Scene`과 같은 `paint()`를 쓰므로, 비용을 나눠도 결과가 갈라지지
않습니다. 배율만 다릅니다.

## 브라우저 한계 대응

### 캔버스 크기

브라우저마다 캔버스의 최대 변 길이와 최대 총 면적 제한이 다릅니다. 정확한 수치는 기기와
버전에 따라 달라지므로 상수로 박지 않습니다. 특히 iOS Safari는 한계를 넘겨도 예외를 던지지
않고 투명한 캔버스를 조용히 돌려줍니다.

`probeCanvasLimit()`을 만들어 이분 탐색으로 실제 할당 가능한 크기를 재고, 알려진 픽셀을 그린
뒤 `getImageData`로 되읽어 확인한 다음 결과를 `localStorage`에 캐시합니다. 이 값으로 내보내기
해상도 선택지를 제한합니다.

4면 여백 프리셋은 원본보다 캔버스를 키우므로 이 문제가 더 일찍 나타납니다. "원본" 옵션은
"측정된 한계까지 유지"를 뜻하며, 축소가 일어나면 결과 화면에 실제 크기를 표시합니다.

### WebP 인코딩

선행 사례가 캔버스 대신 `@jsquash/webp`와 `webp-wasm`으로 WebP를 인코딩합니다. WASM
인코더를 따로 실을 만큼 캔버스의 WebP 출력을 신뢰하지 못했다는 뜻으로 읽힙니다.

시작 시 1x1 캔버스를 `convertToBlob({ type: 'image/webp' })`로 인코딩해 결과 MIME 타입이
실제로 `image/webp`인지 확인합니다. 브라우저가 요청한 타입을 무시하고 PNG를 돌려주는 경우가
있으므로 반환 타입까지 봐야 합니다. 지원하지 않으면 WASM 인코더를 지연 로드합니다.

### 메모리

디코딩된 RGBA는 `가로 * 세로 * 4` 바이트입니다. 5천만 화소 사진 한 장이 약 200MB이고,
처리 중에는 원본 비트맵과 출력 캔버스, 인코딩된 Blob이 동시에 살아 있습니다.

- 배치는 순차 처리합니다. 데스크톱 동시 2건, 모바일 1건을 넘기지 않습니다.
- `File` 객체는 디스크 핸들이므로 미리 전부 ArrayBuffer로 읽지 않습니다.
- 항목마다 `bitmap.close()`를 부르고, 캔버스는 `width = height = 0`으로 되돌려 백킹 스토어를
  즉시 해제하며, 발급한 objectURL을 회수합니다.
- iOS는 메모리가 부족하면 예외 대신 탭을 종료합니다. 배치 큐는 중단 지점부터 재개할 수 있게
  만듭니다.

### 방향 회전

EXIF Orientation은 빠뜨리는 것보다 두 번 적용하는 쪽이 흔한 실수입니다. 최신 브라우저는
`createImageBitmap`에서 기본으로 회전을 적용하지만 구현 차이가 있고, HEIC와 RAW 경로는 이미
회전된 픽셀을 주면서 EXIF는 없습니다.

디코딩 경계에서 정확히 한 번만 정규화합니다. 모든 디코더는
`DecodedImage { bitmap, width, height }`를 반환하고, 이 시점에서 이미 똑바로 선 상태임을
계약으로 둡니다. 브라우저의 자동 회전 여부는 Orientation=6으로 태그한 3x2 JPEG을 시작 시
디코딩해 가로세로가 바뀌었는지 보고 판별합니다.

EXIF는 항상 원본 파일에서 읽습니다. HEIC 변환 결과물에서 읽으면 안 됩니다.

## 브랜드 정규화

EXIF 문자열은 지저분합니다. `NIKON CORPORATION` + `NIKON Z 6_2`, `ILCE-7M4`,
`SIGMA 35mm F1.4 DG HSM | A`, 어댑터를 물린 수동 렌즈의 빈 `LensModel` 같은 것들입니다.

초기 번들 대상 브랜드는 다음과 같습니다.

- 디지털 바디: Canon, Nikon, Sony, Fujifilm, Leica, Panasonic과 Lumix, OM System과 Olympus,
  Pentax, Ricoh, Hasselblad, Sigma, Phase One, Apple, Samsung, DJI, GoPro
- 필름과 중형: Contax, Mamiya, Epson
- 렌즈 전용: Tamron, Zeiss, Voigtlander, Samyang, Viltrox

로고는 밝은 배경용과 어두운 배경용을 따로 만들지 않습니다. `Path2D` 경로에 채움색만 바꾸면
되므로 파일 하나로 두 경우를 모두 처리합니다.

브랜드 목록은 위 전체를 채우되, 정규화 규칙과 테스트 픽스처는 Sony, Canon, Nikon 순으로 먼저
맞춥니다. 실제로 확인할 사진이 이 세 브랜드에서 나오기 때문입니다. 셋 중에서는 소니가 가장
손이 많이 갑니다. `ILCE-7M4` 같은 내부 코드로 찍히므로 모델명 치환표 없이는 읽을 수 있는
이름이 나오지 않습니다.

규칙을 코드가 아니라 데이터로 둡니다.

- `data/brands.json`: `{ id, displayName, logoId, wordmark, aliases, patterns }`. 정규화
  (대문자화, `CORPORATION|CORP|CO|LTD|INC|IMAGING|OPTICAL` 제거, 공백 정리) 후 별칭 완전
  일치, 선두 토큰 일치, 정규식 순으로 먼저 맞는 것을 씁니다.
- `data/models.json`: 브랜드별 모델명 치환입니다. `NIKON Z 6_2`를 `Z 6II`로, `ILCE-7M4`를
  `α7 IV`로 바꿉니다. Model 앞에 붙은 Make 접두사도 제거합니다.
- `data/lenses.json`: 서드파티 렌즈 판별을 바디 브랜드 상속보다 **먼저** 돌립니다. 시그마의
  꼬리표 `| A`, `| C`, `| S`를 떼고 `F1.4`, `f/1.4`, `1:1.4` 표기를 통일합니다.
- 애플은 별도 규칙 모듈로 처리합니다.
  `iPhone 15 Pro back triple camera 6.765mm f/1.78`에서 렌즈 이름과 35mm 환산 초점거리를
  뽑아냅니다.
- `LensModel`이 비면 `LensSpecification`의 초점거리와 조리개 범위로 대체하고, 그것도 없으면
  수동 입력을 유도합니다.

해석된 모든 필드는 `{ value, source: 'exif' | 'rule' | 'manual' | 'fallback' }` 형태로
반환합니다. 이 한 가지 모양 덕분에 "추정값이니 눌러서 고치세요" UI와 수동 편집 패널이 따로
설계할 것 없이 나옵니다.

실제 EXIF 문자열 픽스처 묶음을 만들어 스냅샷 테스트를 붙입니다. 이 모듈이 조용히 망가지기
가장 쉬운 곳입니다.

## 모듈 구조

파일 하나가 목적 하나를 갖도록 나눕니다.

```
src/
  core/                      React와 DOM에 의존하지 않는 영역
    io/sniff.ts              매직 바이트로 파일 종류 판별 (확장자 신뢰 금지)
    io/decode/{index,jpeg,heic,raw}.ts   decode(file) -> DecodedImage
    io/orientation.ts        회전 변환 수학과 브라우저 자동 회전 탐지
    exif/{read,map,format}.ts            태그 -> PhotoMeta -> 표시 문자열
    brand/{normalize,resolve}.ts + data/*.json
    logos/registry.ts        brandId -> Path2D 지연 로드
    layout/types.ts          Scene, Node, LayoutInput, LayoutServices
    layout/presets/{infoBar,matte,overlay}.ts    순수 layout()
    layout/{registry,primitives}.ts      줄바꿈, 말줄임, 행 배치, 구분선
    layout/options.ts        PresetOption 선언 타입과 기본값 병합
    layout/template.ts       템플릿 토큰 치환, 빈 토큰과 구분자 정리
    paint/{paint,fonts}.ts   Scene x ctx x pxPerUnit -> 픽셀
    limits/canvasLimits.ts   한계 측정과 clampExportSize()
    export/{resolution,encode}.ts        원본/4K/2K/SNS, convertToBlob
    export/webpSupport.ts    캔버스 WebP 지원 탐지와 WASM 폴백
    render/renderOne.ts      단일 이미지 오케스트레이션
  worker/{render.worker,client}.ts       타입이 붙은 RPC, transferable 전달
  batch/{queue,zip}.ts       순차 큐, 취소, 항목별 오류 격리, client-zip
  state/                     선택된 프리셋, 옵션, 큐 상태
  i18n/                      ko, en 사전
  ui/                        드롭존, 미리보기, 프리셋 선택, EXIF 편집 패널, 내보내기 대화상자
```

`core`는 번역된 문자열을 반환하지 않고 키와 구조화된 값만 반환합니다. 포매터는 로케일을 인자로
받습니다.

## 구현 순서

위험이 큰 것부터 앞에 둡니다.

1. **UI 없는 스파이크.** 캔버스 한계 측정, 방향 회전 탐지, 매직 바이트 디코딩 분기. 실제
   아이폰에서 확인합니다. 이 둘은 실패해도 조용히 빈 이미지나 누운 이미지를 내놓기 때문에 가장
   먼저 잡아야 합니다.
2. `layout` 과 `paint` 분리, 프리셋 한 개, 배율 동등성 테스트.
   선언적 옵션 스키마와 자동 생성 설정 패널, 템플릿 토큰 치환을 여기서 함께 만듭니다.
   프리셋을 늘리기 전에 이 뼈대가 서 있어야 합니다.
3. 로고 SVG를 `Path2D`로 바꾸는 빌드 스텝, 폰트 로딩 전략.
4. 브랜드 정규화와 픽스처 테스트.
5. EXIF 수동 편집 패널.
6. 나머지 프리셋 두 개.
7. HEIC, 그다음 RAW.
8. 배치와 ZIP. 메모리 버그를 배수로 키우므로 마지막입니다.
9. i18n 문자열 정리와 배포.

구현 계획은 두 단계로 나눕니다. 1단계는 1번부터 5번까지로, JPEG 한 장을 넣어 프리셋 하나를
적용하고 내려받는 경로를 끝까지 완성합니다. 2단계는 6번부터 9번까지의 확장입니다. 1단계가
동작하기 전에는 확장 작업을 시작하지 않습니다.

## 검증

- **단위 테스트(Vitest):** 브랜드 정규화 픽스처 스냅샷, 레이아웃 원시 함수(줄바꿈, 말줄임),
  해상도 클램프 계산.
- **배율 동등성 테스트:** 같은 `Scene`을 배율 1.0과 0.25로 그린 뒤, 앞의 것을 축소해 두
  결과가 지각적으로 같은지 확인합니다. 레이아웃 추상화가 새지 않도록 붙잡아 두는 테스트입니다.
- **수동 확인 목록:** 아이폰 HEIC 원본, DSLR RAW 한 개 이상, Orientation=6 태그가 붙은 JPEG,
  EXIF가 아예 없는 필름 스캔, 5천만 화소급 대형 JPEG. 데스크톱 크롬과 iOS Safari에서 각각
  확인합니다.
- **엔드투엔드:** 개발 서버를 띄우고 브라우저 도구로 파일을 넣어 미리보기가 나오는지,
  내보낸 파일이 실제로 열리는지, WebP 출력이 정상인지 확인합니다.

## 남은 위험

- **로고 상표.** 카메라와 렌즈 브랜드 로고는 등록상표입니다. 사용자가 번들 방식을 선택했고
  기성 앱들도 같은 방식이지만, 공개 배포이므로 이 위험은 남아 있습니다. 로고를 브랜드별로
  교체하거나 제거할 수 있게 레지스트리를 데이터 주도로 만들어 두면 나중에 대응할 여지가
  생깁니다.
- **RAW 프리뷰 해상도.** 내장 프리뷰는 센서 해상도가 아니고 긴 변 1600px 정도인 경우도
  있습니다. RAW에서는 "원본" 선택지가 사실과 다르므로 실제 프리뷰 크기를 화면에 표시합니다.
- **PNG 대용량 출력.** 5천만 화소 PNG는 다루기 어려운 크기가 됩니다. 큰 해상도에서는 JPEG나
  WebP를 권합니다.
- **배치 다운로드.** `showSaveFilePicker`는 크로미움 계열에만 있습니다. 그 외 브라우저에서는
  Blob을 통째로 만들어야 하므로 배치 장수 상한을 두고 미리 안내합니다.
